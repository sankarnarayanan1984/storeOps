# Reflection — demonstration run `2026-10-30-bulk-status`

**Run:** shift handover bulk update (`PROMPT.md`) → 4 sprints (activities, alerts, reports, programmes), 20 ACs, all **PASS 100 on iteration 1**; 145 tests, 99.14 % line coverage; ≈ 546 k measured tokens (Generator + Evaluator), **$2.18–$10.92** at the published claude-opus-5-5 rates ($4 in / $20 out per MTok; range because usage isn't split into input/output). Evidence: `.harness/reviews/2026-10-30-bulk-status/`.

## What the harness did well
- **Architecture held across a cross-cutting feature.** The feature touched all five modules, yet nothing crossed a boundary except through `activity.handover_completed` and the type-only `StaffReader`. Programmes and reports react in their own `*.subscribers.ts`. The Evaluator confirmed A4 with line evidence (e.g. `programmes.subscribers.ts:6`, `programmes.service.ts:223`). That is failure modes 1 and 4 prevented by design, not by luck.
- **ACs written for testing produced tests that check outcomes.** Contract ACs named concrete ids, error codes and read-backs. For example, S1-AC2 requires A3 to "still read DONE" after a rejected item. The generated tests assert those outcomes rather than status codes (failure mode 3, check B3).
- **Approval caught a gap before any code existed.** The Planner's first spec touched only activities and alerts. My `CHANGE` sent it back, and it returned a 4-sprint plan with two explicit decisions. In the same revision it found and fixed its own wrong assumption about the `createActivity` helper's default store. Fixing this at the spec stage cost about 2 minutes; fixing it after generation would have meant a re-plan.
- **The Evaluator looked beyond its brief.** It flagged README quick-start lines that neither the Generator nor my pre-run note accounted for, and judged a Generator edit to an existing test as stricter rather than weaker before passing C3.

## Where it fell short
1. **The loop was never stressed.** All 64 check results (36 of them LLM judgements) were PASS, so this run is no evidence that retry, CONDITIONAL PASS or escalation work. Those paths were only verified on the baseline: planted imports, a `jest.config.js` edit, synthetic check files fed to `compute-verdict.mjs`. A 100 % first-pass rate is also ambiguous: either the skills were strong, or the LLM checks are too lenient. One run can't tell which.
2. **Context leaked through prompts instead of files.** Every Evaluator after sprint 1 needed me to explain, in its prompt, that `automated-checks.json`'s changed-files list is *cumulative since approval* and which README lines predated the run. That breaks Design Brief decision **D2** ("all context through handoff files"). The instructions were ungoverned (not in any skill), and a different orchestrator could easily omit them and get false C3 failures.
3. **The token estimate is not trustworthy.** The Monitor's chars ÷ 4 estimate came in roughly 2× below measured usage on every sprint (73 k vs 165 k; 61 k vs 117 k; 54 k vs 125 k; 64 k vs 139 k). That makes it useless for cost trends. The estimate counts files read, but not tool output, test logs or the agent's own reasoning.

## One concrete improvement
**Give each sprint its own diff base, recorded in a file.** When a sprint starts, the orchestrator runs `run-checks.mjs --sprint-start N`. This hashes every file under `src/`, `tests/` and `README.md` into `.harness/output/sprint-N-baseline.json`, the same way the D3 protected-file snapshot works. `run-checks.mjs` then reports `changed.files` relative to that baseline, so the Evaluator sees only this sprint's changes. Pre-run and earlier-sprint edits drop out without anyone explaining them. This removes the prompt-borne instructions in shortfall 2 and restores D2's assumption.

Next in priority: have the Monitor record measured agent usage from the platform instead of estimating (shortfall 3). Then add a `selftest` sprint that plants one known violation per hard gate and expects FAIL, so every run exercises the rejection path (shortfall 1).
